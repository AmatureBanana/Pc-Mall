# 本人取消与订单超时

任务19继续使用统一订单服务、Session归属、服务端Clock和既有库存预占。成交快照与购物车均不因取消而改写。

## 主动取消

`POST /api/orders/{number}/cancel`，请求体为空或 `{}`，须携带当前Session的CSRF凭证。不接受客户端用户、状态、时间或取消原因；额外字段、非对象及多段JSON返回400 / `INVALID_CANCELLATION_INPUT`。

- 仅本人 `PENDING_PAYMENT` 可转为 `CANCELLED`，记录 `cancellationReason: USER` 和UTC微秒精度 `cancelledAt`。
- 已取消同单重试返回原结果，保留首次原因和时间，包含已被扫描取消为 `TIMEOUT` 的情况。
- `PAID`、`COMPLETED` 返回409 / `ORDER_NOT_CANCELLABLE`。取消为终态，不能再支付。
- 未登录返回401；CSRF无效返回403；其他用户和不存在的订单均返回404 / `ORDER_NOT_FOUND`。
- 持久化故障沿用503 / `CART_UNAVAILABLE`；未提交的取消可安全重试。

## 每分钟扫描

`OrderTimeouts.scan()` 使用 `0 * * * * *` 每分钟执行。正式运行启用Spring调度；`test` profile关闭自动调度，测试通过公开扫描入口和可控Clock验证真实行为。

每轮固定本轮截止时间，按订单号游标每批读取100笔 `PENDING_PAYMENT` 且支付截止不晚于本轮时间的订单。每笔独立事务，取得订单行锁后再次检查状态和当前时间，只有仍待支付且已经到期才取消，记录 `TIMEOUT` 和实际处理时间。扫描延迟不改变支付期限：支付仍在取得订单锁后要求 `now < paymentDeadline`，恰好截止也拒绝。

单笔失败记录订单号和异常，继续处理其余订单；游标经过失败项，避免它阻塞同轮后续订单。下一轮从头检查尚待支付的到期订单。查询级故障交由调度器记录，后续分钟重新扫描；扫描没有只能执行一次的内存领取状态，服务重启可继续处理。

## 状态与库存一致性

支付、主动取消和超时处理先取得同一订单锁。取消路径共用 `cancelPending`，依次锁定预占头及按ID升序的商品；复用 `ProductInventory.release` 按持久化的汇总数量释放一次预占。

释放库存、预占转 `RELEASED`、订单转 `CANCELLED` 及取消信息都加入同一MySQL事务。任一步失败全部回滚，不会永久写入取消终态后丢失释放责任；重试、重复扫描及多个扫描实例竞争均由订单锁和预占幂等保护。支付和取消竞争只有一个状态转换成功，支付不再次改库存。取消不会恢复原购物车。

V27新增 `cancelled_at`、`cancellation_reason` 和到期查询索引，未修改已执行迁移。详情及本人列表返回新增两个字段，未取消时为null。允许旧取消记录两字段均为null；有取消信息时要求状态为CANCELLED、原因仅USER/TIMEOUT且时间非空。

页面提供待支付订单的二次确认取消，展示服务端取消原因、时间和当前状态。网络结果不明确时保留同单重试和重新读取入口；权限、状态拒绝及会话失效明确展示。未新增支付倒计时。
