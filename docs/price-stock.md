# 价格与可售库存契约

任务07复用任务05商品管理、统一Session/CSRF和共享审计。管理员在 `/#admin/products` 的商品详情中调价和增减库存。公开列表与详情继续读取同一张商品表，金额为CNY精确十进制字符串。

## 管理接口

全部接口要求ADMIN，匿名401、普通USER为403；POST需要当前Session的CSRF令牌。

| 路径 | 输入与结果 |
| --- | --- |
| POST `/api/admin/products/{id}/price` | `{revision,price,reason}`；价格为大于零、最多10位整数及2位小数的字符串；存储及返回固定两位；版本过期409/PRODUCT_CONFLICT |
| POST `/api/admin/products/{id}/stock` | `{delta,reason}`；delta为非零32位整数，正数入库、负数扣减可售量；在锁内基于最新值累加，无需提交绝对库存或旧版本；不足或越界409/STOCK_CONFLICT |
| GET `/api/admin/products/{id}` | 既有详情增加`reservedStock`；`product.stock`始终是可售库存，`revision`和`product.revision`相同 |
| GET `/api/admin/products/{id}/audit` | 复用最近100条共享审计；PRICE/STOCK记录操作者、时间、对象、前后金额或库存、版本、原因；库存还记录delta和预占量 |

reason为去首尾空白后非空、最长500个Unicode字符的文本。缺字段、非法金额/数量、未知字段及直接覆盖`stock`、`reservedStock`均400。不允许零增减；相同价格在版本检查后返回当前值，不增加版本或重复审计。下架草稿也可调整。

管理操作先锁商品行，再执行带版本/范围条件的UPDATE；业务、版本及审计在同一事务中提交。审计故障503且整体回滚。资料编辑、参数、上下架、价格及库存变动均增加商品`revision`，公开商品也返回该版本，供后续重验使用；参数`dataVersion`保持参数来源/版本含义，不冒充价格版本。

库存按增减量执行；页面需重新载入才能解决资料表单或调价的版本冲突。资料和调价表单分别保留编辑版本；库存响应即使取得了较新的商品版本，也不能把旧资料或旧价格输入自动升级为可覆盖其他管理员修改的版本。

## 预占与释放

V12增加`reserved_stock`及独立的`stock_reservations`、`stock_reservation_items`。`stock`是立即可售量；`reserved_stock`是尚未释放/结转的预占量，不能从管理接口直接修改。二者非负且合计不超过2147483647，管理补货不会占用既有预占未来释放所需的数值空间。

V13在头记录上保存不可变数量快照及创建尝试标识，回填既有明细且保留原表。写操作通过同一次头记录当前锁定读取得状态和数量，避免参与已有REPEATABLE READ外层事务时读到旧明细。创建标识只区分本次新建与已存在记录，不依赖MySQL可配置的影响行数口径，也不扫描新预占明细的空范围。管理调整与预占/释放共用`InventoryMapper.change`的版本、非负及总量条件保护。

`ProductInventory`是后续订单复用的公开后端业务服务，无浏览器预占接口：

- `reserve(reference, quantities)`接收服务端汇总后的商品ID到正整数数量的映射，只预占当前上架且足量的商品；可售量减少、预占量增加、商品版本变化和明细保存整体提交。
- 同reference同内容的有效预占重试返回原结果；内容不同或已释放后重用拒绝。reference为1～100位ASCII字母数字及`._:-`，首位字母数字，区分大小写。
- `release(reference)`仅依据已存明细恢复可售量并减少预占量，不接收客户端释放数量；保留明细并转为RELEASED，并发或重复释放只生效一次。下架不阻止已有预占释放。
- `reservation(reference)`只读查询持久化状态和数量；不存在返回null。

固定锁序为预占头记录（涉及预占时）→全部商品ID升序→库存条件更新及明细/状态写入。管理员单SKU操作使用同一商品行锁。批次先按固定顺序取得全部商品锁，再修改；任一失败回滚整批。

方法以REQUIRED事务加入调用方，未来订单必须在同一外层事务中绑定订单身份、购物车清理、快照和订单状态检查。支付/取消权限、成交快照、完整幂等请求绑定及支付结转由后续订单任务接入；本票没有新增订单或支付入口，也不声称完成这些端到端场景。支付及完成不得再次扣减可售库存。任何后续写入都须遵守相同锁序，不能直接覆盖商品库存或历史成交快照。
